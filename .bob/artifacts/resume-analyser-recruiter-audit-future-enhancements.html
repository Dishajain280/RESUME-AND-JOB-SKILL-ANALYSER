🚨 Part 1 — Critical Issues a Recruiter Will Spot

These are the issues most likely to cost you the position. A senior reviewer will open each file and find these within minutes.

Critical #1 — Architecture
In-Memory Store Is the Data Layer — No Database
store.py uses plain Python dicts (_resumes, _analyses). Every server restart wipes all data. There is no file persistence, no SQLite, no PostgreSQL. The README says "replace with a real DB", which means the candidate knew but shipped it anyway. A recruiter sees this as half-built. Even a simple SQLite + SQLAlchemy integration takes ~30 minutes and would flip this from a red flag to a green tick.
Critical #2 — Security
Hard-Coded Default SECRET_KEY Shipped in Source Code
config.py line 23: SECRET_KEY: str = "change-me-in-production-use-a-long-random-string". This default is committed to the repo. Even though there is no active auth flow, the skeleton imports python-jose and passlib — meaning a reviewer knows auth was planned. Shipping a known-bad secret key is a textbook security fail. It should be Field(...) with no default, forcing the environment to always provide it.
Critical #3 — Logic Bug
ATS Tips Function Is Broken — Always Returns the Same 5 Tips
analyser.py lines 362–366: _ats_tips_for_resume() checks if "table" is in the resume text to decide what to return, but the branch that uses that condition never executes — both paths return tips[:5]. The function signature promises contextual tips but delivers a static slice regardless of resume content. A recruiter testing with a complex resume will see the same 5 generic tips every single time. This is a dead-code / untested logic bug.
Critical #4 — Backend Reliability
No Rate Limiting, No File-Size Pre-Check, No Auth on Any Endpoint
Every endpoint is fully open. File size is validated after the full file is read into memory (not streamed), meaning a 500 MB file will be buffered before being rejected. There is no rate limiting on /resume/upload or /analysis/ — a simple loop could OOM the server. The JWT/auth skeleton is declared in config.py (ACCESS_TOKEN_EXPIRE_MINUTES, SECRET_KEY) but never wired to any route. A senior engineer sees declared intent with zero follow-through.
Critical #5 — Duplicate Dependency & Test Gap
httpx Listed Twice in requirements.txt + Only 4 Tests Total
requirements.txt lines 17 and 20 both declare httpx==0.27.0. While pip resolves this without error, it signals that the file was not reviewed before commit. More importantly, there are only 4 test functions covering the entire backend. There are zero tests for: the parser (parser.py), the skill extraction logic, the extractor fallback paths, education scoring edge cases, or any frontend behaviour. A project presented as "production-quality" needs a real test suite.

⚠️ Part 2 — Code Smells & Technical Weaknesses

Weakness #1 — NLP
Skill Matching Is Pure String Matching — Not Real NLP
Despite importing spacy==3.7.4, sentence-transformers==2.7.0, and scikit-learn in requirements.txt, none of these libraries are actually called in the analysis pipeline. The entire "AI" in "AI Resume Analyser" is re.compile(...).search(text_lower). That is keyword spotting, not NLP. If a recruiter or interviewer asks "walk me through your NLP approach", the honest answer is regex over a dictionary.
Weakness #2 — Parser Accuracy
Experience & Education Parsers Are Fragile
parser.py _extract_experience() splits on blank lines and guesses job title from lines[0] and company from lines[1] — this breaks on any non-standard resume format. Single-column resumes with dense text, two-column PDFs, or resumes with dates on the same line as job title will all parse incorrectly. _extract_education() has a hardcoded field: "" — the field of study is never populated, affecting the education score.
Weakness #3 — Scoring Logic
Experience Score Has an Uncontrolled Ceiling Bug
analyser.py _compute_experience_score() line 221: when ratio >= 1.0 it returns min(100.0, 70.0 + ratio * 10). For a candidate with 20 years vs a 3-year requirement, ratio = 6.67, giving 70 + 66.7 = 136.7 which is clamped to 100 — correct numerically but the base of 70 means any matching candidate starts at 70/100 minimum. If required_years = 0, it hard-returns 85 for everyone, hiding true gaps.
Weakness #4 — Frontend Step 3
Step 3 in the Wizard Is a Dead UI State
AnalysePage.tsx lines 113–121: Step 3 renders "Review & Submit" with only a "Back" button. There is no Analyse button, no summary of what will be submitted, and no way to proceed from step 3. The only way to actually run the analysis is on Step 2. Step 3 is visible in the stepper but functionally unreachable for the intended purpose — users who click "next" from step 2 end up confused. The handleAnalyse is only called from the JobDescriptionForm inside step 2.
Weakness #5 — Share Feature
"Share" Button Shares a URL That Won't Work After Server Restart
ResultsPage.tsx line 19: clicking Share copies the URL (e.g. /results/abc-123) to the clipboard. But the analysis is stored in-memory (store.py). On any server restart, that analysis_id is gone. The share feature promises a persistent link but delivers a broken one every time. This is a direct consequence of Critical #1 but also a user-facing feature that actively misleads users.
Weakness #6 — Production Config
reload=True in production entry point. main.py line 83: uvicorn.run(..., reload=True). File-watching reloaders are for development only — they add significant overhead and can cause race conditions in production. This is the __main__ block so it only runs via python main.py, but it's still a flag that was not cleaned up.
Weakness #7 — Frontend Error Handling
Axios error messages surface raw server internals. api.ts lines 12–16: the interceptor sets err.message = detail, which can expose internal error strings (e.g. Python tracebacks if the global handler ever fails). The toast.error(msg) calls in ResumeUploader.tsx and AnalysePage.tsx blindly display whatever comes back. In production, a sanitised "Something went wrong" message should be shown to users while the raw error is only logged.

✅ Part 3 — What Was Done Well

Clean Architecture & Project Structure
Clear separation of concerns: extractor → parser → analyser → store → endpoint. Service layer is dependency-injected by import, Pydantic v2 schemas are well-defined, and the API is versioned (/api/v1/). This is senior-level organisation.
Strong Frontend Component Design
React components are small and purpose-built. ScoreGauge, SkillMatchGrid, SkillChart are reusable. Form validation uses Zod + react-hook-form correctly, with schema mirroring the backend constraints (min 50 chars, max 10,000).
Structured Logging + Global Error Handler
structlog is used consistently across all services. The global exception_handler in main.py catches unhandled errors. Request timing middleware adds X-Process-Time headers — a genuinely production-oriented detail.
Comprehensive Skill Knowledge Base
140+ skills across 7 categories with canonical name normalisation, alias resolution, and per-skill confidence scores. This is thorough domain modelling that shows real thought about the problem.

🚀 Part 4 — Future Enhancements Roadmap

Grouped by impact tier. Implement high-priority items first — they directly fix recruiter concerns and add real demonstrable value.

# Feature Priority What It Adds
1 Persistent Database (SQLite → PostgreSQL) High Replace in-memory store with SQLAlchemy + Alembic migrations. Fixes history, share links, and restarts. Makes the app actually production-ready.
2 User Authentication (JWT) High Wire the existing python-jose / passlib skeleton into real register/login endpoints. Each user sees only their own analyses. The infrastructure is 80% already declared in config.py.
3 Real NLP with spaCy / Sentence-Transformers High Replace regex skill matching with spaCy NER + sentence-transformers semantic similarity. Catches "ML Engineer" matching "Machine Learning", synonyms, and context-aware matches. These libraries are already in requirements.txt — just not used.
4 PDF Export of Analysis Report High Generate a downloadable PDF of the full analysis using weasyprint or a React-to-PDF library. The "Export" button already exists in the UI (currently just calls window.print()).
5 Resume Score Comparison (Multi-JD) Medium Allow users to upload one resume and compare it against multiple job descriptions side-by-side. Show a comparison table of scores. Great for job seekers choosing between offers.
6 LLM-Powered Recommendations (OpenAI / Gemini API) Medium Replace the static template-based recommendations with an LLM call that generates personalised, context-aware advice (e.g. "Given your 4 years of Python and missing Kubernetes, here's a 30-day plan..."). Add an optional API key field in settings.
7 Resume Builder / Keyword Injector Medium After analysis, show which exact phrases from the JD are missing in the resume, and offer to generate bullet points or summary rewrites that include them. Turns the tool from an analyser into a resume editor.
8 Job Description Auto-Import (URL Scraping) Medium Let users paste a LinkedIn / Indeed / Greenhouse job URL instead of copy-pasting text. Use httpx + BeautifulSoup to scrape and auto-fill the description field. httpx is already a dependency.
9 Score Trend Dashboard Medium In the History page, add a line chart showing score progression over time per job category. Shows users whether their skills are improving. Recharts is already in the frontend bundle.
10 Docker Compose Setup Medium Add Dockerfile for backend + frontend and a docker-compose.yml. One-command startup removes the "it works on my machine" problem and is a strong signal of DevOps awareness. Directly mentioned in the README as missing.
11 Resume Anonymisation / Privacy Mode Low Strip PII (name, email, phone, address) from the stored resume before persisting to the database. Show a "Privacy Mode" toggle. Strong differentiator for GDPR-conscious users or enterprise HR teams.
12 Role-Specific Skill Templates Low Pre-built skill requirement profiles (e.g. "Data Scientist", "DevOps Engineer", "Product Manager") that users can load as a JD template. Lowers friction for people who don't have a specific JD at hand.
13 Salary Range Estimator Low Based on matched skills, experience years, and location field, show a salary band estimate sourced from a static dataset or a public API (e.g. levels.fyi data). Adds immediate tangible value to users.
14 Browser Extension Low A Chrome/Firefox extension that detects when a user is on a job posting page, extracts the JD text, and opens a side panel showing the match score against their saved resume. Turns the web app into an ambient tool.
15 Multi-Language Resume Support Low Expand section detection and skill matching to handle resumes in French, German, Spanish, and Portuguese (large markets). spaCy has multilingual models (xx_ent_wiki_sm). Enables international use cases.
